## 1. DeepFM：广告点击率预测

仓库：[shenweichen/DeepCTR-Torch](https://github.com/shenweichen/DeepCTR-Torch)。

建议题名：**基于 DeepFM 的广告点击率预测与计算复杂度分析**。

输入 → 机制 → 中间判断 → 输出：
匿名化广告特征 → 类别嵌入、FM 二阶交互与 DNN 分支 → 合并分支得分 → 点击概率，供候选广告排序使用。Criteo 的匿名特征不能擅自解释为具体商品、技能或消费偏好。

与本科经历的衔接：结构化数据清洗、分类建模、集成思想、预测评价，工程背景可落在平台广告排序。

已核对：
- `examples/run_classification_criteo.py`：缺失处理、编码、训练、验证、测试，输出 AUC/LogLoss。
- `examples/criteo_sample.txt`：表头加 200 条数据，仅适合演示。
- `deepctr_torch/models/deepfm.py`：线性、FM 与 DNN 分支；支持分支开关，可开展消融。
- `deepctr_torch/layers/interaction.py`：FM 通过“和的平方减平方的和”计算交互，适合展开复杂度推导。
- `setup.py`：当前 PyTorch 依赖声明；本轮未安装。

建议实验：DeepFM 与 LR、FM、DNN 比较；考察样本量、嵌入维度与网络宽度；报告 AUC、LogLoss、参数量、训练/推理耗时；分析低频类别、未见类别和类别不平衡。

需补：取得正式数据或合理规模子集；示例在切分前拟合编码器与 MinMaxScaler，正式实验应先划分，再仅在训练集拟合预处理并处理未知类别。上述为代码审查，不是已经修复或复现。

## 2. LightGCN：电影个性化推荐

仓库：[RUCAIBox/RecBole](https://github.com/RUCAIBox/RecBole)。

建议题名：**基于 LightGCN 的电影个性化推荐与计算代价分析**。

用户—电影评分/交互 → 按明确规则形成训练交互图 → 多层邻居聚合与层间平均 → 对候选电影打分并输出 Top-K。若把评分转为隐式偏好，需明确转换规则，不能把评分直接称为点击日志。

与本科经历的衔接：用户画像、用户行为、平台推荐，以及既有电影相关数据分析经历。此处使用 MovieLens 数据，不能沿用先前项目指标。

已核对：
- 仓库包含 `dataset/ml-100k/` 的交互与用户、物品数据。
- `recbole/model/general_recommender/lightgcn.py`：图构建、稀疏聚合、成对排序损失和全候选排序。
- `recbole/quick_start/quick_start.py`：训练/验证/测试划分、验证选模、最终测试。
- `recbole/properties/overall.yaml`：Recall、NDCG、MRR 等指标配置及全候选评价。
- 已有 BPR 等基线；统一框架降低对照实验的组织成本。

建议实验：LightGCN 主模型，BPR/NeuMF 等对照；改变图层数、嵌入维度与交互稀疏度；报告 Recall@K、NDCG@K、训练和推荐耗时；检查长尾电影、低活跃用户与冷启动局限。

需补：固定数据划分、负采样与候选集合口径，区分图传播与全候选打分的成本。源码调用 SciPy 的私有 `A._update` 接口，且依赖 Ray，现代环境需做版本适配核验。这是环境项评分为 3 的主要原因。

## 3. PJFNN：招聘平台人岗匹配

仓库：[RUCAIBox/RecBole-PJF](https://github.com/RUCAIBox/RecBole-PJF)。

建议题名：**基于 PJFNN 的人岗匹配推荐与性能分析**。

求职者文本与岗位文本 → 两个 TextCNN 分支提取表示 → 表示逐元素交互与 MLP 打分 → 排序候选岗位。训练还需要求职者—岗位的交互或匹配监督。

与本科经历的衔接最直接：将已有岗位技能需求分析拓展为推荐任务。背景理解与文本清洗经验可复用；原有岗位描述数据并不自动提供求职者文本、交互或匹配标签。

已核对：
- `recbole_pjf/model/pjfnn.py`：TextCNN、匹配打分与 BPR 损失。
- `run_recbole_pjf.py`、`recbole_pjf/quick_start/quick_start.py`：启动、训练、验证和测试。
- `dataset/zhilian/prepare_zhilian.py`、`dataset/jobrec/prepare_jobrec.py`：外部原始数据处理脚本。
- README 列出天池智联与 Kaggle 数据来源，本轮未下载验证其可得性。

建议实验：主模型 PJFNN，对照简单文本相似度和 BPR/适当文本模型；固定相同划分与候选集合，比较 Recall@K、NDCG@K 和匹配耗时；分析相似岗位、低信息简历与新岗位的失败。

实质缺口：
- 智联脚本中的 `direct` 字段通过随机数生成，不能据此声称还原真实求职/招聘双向行为；课程可先限定单向岗位推荐。
- jobrec 脚本的用户—岗位筛选存在需审查的键使用：在岗位计数判断中使用了用户索引，不能直接沿用结果。
- 需核对数据字段、标签语义、预处理和 RecBole 版本兼容性。数据项为 5，因此本轮将它列为条件性推荐，尚不作为默认实施题目。

## 4. HDPO：单门店库存补货

仓库：[MatiasAlvo/Neural_inventory_control](https://github.com/MatiasAlvo/Neural_inventory_control)。

建议题名：**基于可微仿真策略优化的单门店库存补货研究与计算代价分析**。

现有/在途库存、成本、提前期与可用需求历史 → 神经策略决定订货量 → 已知库存仿真更新状态并累计成本 → 对仿真轨迹求梯度更新策略，最终输出补货决策。

与本科经历的衔接：需求分析 → 库存与成本决策，适合大数据管理与应用的业务取向。方法学习难度主要来自多期策略优化与可微仿真。

已核对：
- `environment.py`：库存仿真、到货更新及持有/缺货成本。
- `data_handling.py`：README 和目录确认数据生成入口；本轮未逐行审查该文件。
- `main_run.py`、`trainer.py`：数据划分、训练、验证和测试函数；训练通过模拟累计损失反向传播。
- `neural_networks.py`：单门店网络、base-stock/capped-base-stock 等策略。
- `config_files/`：合成需求与真实零售配置；仓库包含预处理 Favorita 数据文件，本轮仅核对目录未读取二进制数据。

建议先限于一个门店、合成需求、一个主策略与两类库存规则对照。考察提前期、缺货成本和需求变化；报告平均成本、满足程度与运行耗时；结合实际结果讨论需求分布变化和错误成本设定。

需补：默认配置 20000 epochs、测试 32768 条轨迹×5000 期，课程实验须缩小规模；这属于配置大小，不是本机耗时。README 声称 train 后自动测试，但当前 `main_run.py` 使用 if/elif 分支，训练分支不会直接进入测试分支，需明确选模/保存/测试调用。未来信息 oracle 不能当作可部署普通基线。

## 5. 备选：LightGBM 零售销量预测

仓库：[Mcompetitions/M5-methods](https://github.com/Mcompetitions/M5-methods)，核查 A1 子目录。

建议题名：**基于 LightGBM 的零售商品销量预测与计算代价分析**。

历史销量、价格与日历 → 滞后/滚动特征 → LightGBM → 未来销量。与已有时间序列和集成预测经历相衔接。

已核对 A1 的预处理、训练和预测脚本及 README，代码包含 LightGBM Tweedie 目标和多套分组模型。课程应缩为一家门店或一个品类，与季节性朴素预测等基线比较，避免照搬全量竞赛集成。

降低优先级的原因：
- 原始数据需外部获取；A1 README 所述预训练文件与 requirements 文件，在当前目录树对应位置仅见占位或缺失，不能按 README 宣称预训练资源齐备。
- 路径硬编码及旧 LightGBM 调用需适配。
- 所查训练脚本中的 `valid_mask` 是 `train_mask` 子集，不能作为独立留出验证证据，需重新设计滚动验证。
- 主算法与同学 XGBoost 选题同属提升树，虽然工程问题不同，方法差异小于推荐系统方向。
